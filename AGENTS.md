# AGENTS.md — правила для ИИ-агента в харнессе озвучки

Ты работаешь в харнессе `vox`: озвучка книг, рекламы, слоганов и голоса для видео на
Gemini 3.8 Flash TTS. Пользователь общается по-русски, пиши ему тоже по-русски.
Сначала прочитай этот файл, затем [docs/GEMINI_TTS.md](docs/GEMINI_TTS.md) и
[docs/SCRIPT_GUIDE.md](docs/SCRIPT_GUIDE.md).

## С чего начинать каждый раз

```
python -X utf8 vox.py --book projects/<проект> next      # следующий шаг с готовой командой
python -X utf8 vox.py --book projects/<проект> status    # сводка
```
`next` смотрит на файлы проекта и называет ближайший шаг. Держать конвейер в голове не нужно.
Если `next` предлагает платный шаг, остановись и спроси пользователя (см. ниже).

Те же команды доступны как инструменты MCP (`mcp_server.py`, подключение — `.mcp.json`; один раз выполните `python setup_agent_files.py`): `vox_next`,
`vox_status`, `vox_show_job` и `vox` для любой бесплатной команды. Платное MCP не выполняет — его
запускают в терминале с `--yes` после согласия пользователя. В Claude Code есть навык `.claude/skills/vox`.

## Неизменные правила

1. **Платное — только с явного разрешения пользователя в этом разговоре.** Это `synth --yes`,
   `pilot run --yes`, `clips render --yes`, `say --yes`, `cast design/audition --yes`, `pron trial --yes`,
   `attribute run --yes`, `tts.py --yes`, а также `qc run` при `asr = gemini`.
   Перед просьбой о разрешении покажи вывод `plan` или `clips plan`: число запросов, символы, оценку цены.
   Разрешение действует на названный объём, а не на всё будущее.
2. **Никогда не повторяй POST вручную.** Если исход неизвестен (`ledger show` → «неизвестный исход»),
   сообщи пользователю. `ledger resolve` выполняется только после того, как человек подтвердил, что запрос
   не прошёл (например, по списку Batch в AI Studio).
3. **Не редактируй руками** `releases/`, `audio/cache/`, `audio/ledger.jsonl`, `audio/batches/*/submission.json`,
   `text/`. Это журналы и замороженные данные; всё меняется только командами.
4. **Слова автора неприкосновенны.** Можно: CAPS для акцента, «ё», пунктуация, теги из таблицы Google,
   разбиение блока. Опечатку исправляй только с полем `edit: "причина"`. `attribute import` и `check`
   отклонят любое изменение слов без причины.
5. **Ключи.** API-ключ лежит только в `.env`. Не печатай его, не копируй в отчёты, не коммить `.env`
   и файлы `*Cred*`.
6. **Не утверждай за человека.** `approve`, `cast accept`, `pron accept` и `qc accept` означают
   «человек прослушал или прочитал и согласен». Агент может предложить список, но выполняет команду
   только по прямому указанию.
7. **Не выдавай сигналы проверки за дефекты, а их отсутствие — за качество.** ASR находит кандидатов;
   ударение и тембр проверяет только слух.

## Книга: полный цикл

| Шаг | Команда | Что делает агент |
|---|---|---|
| 1 | `init projects/<имя> --source <файл>` | создаёт проект |
| 2 | `ingest` | проверяет `text/sections.json`: служебные разделы (аннотация, реклама) → `"audio": false` |
| 3 | `cast add …` | заводит главных персонажей с алиасами (имя, прозвища): тогда draft сам узнает «сказал Вашер» |
| 4 | `draft` | черновик: речь и ремарки разделены |
| 5 | написать `attribution/BOOK_NOTES.md` | 10–30 строк: кто есть кто, как обращаются друг к другу, особые формы речи (телепатия, письма), стиль книги. Это попадёт в каждый пакет |
| 6 | `attribute prepare` | пакеты `attribution/packets/*.md` |
| 7 | ответить на каждый пакет | см. «Как отвечать на пакет атрибуции»; длинная книга — «Параллельная атрибуция» |
| 8 | `attribute import` | применить; ошибки исправить и импортировать снова (`attribute status` покажет, где) |
| 9 | `attribution/REVIEW.md`, `attribution/ROLES.md` | перепроверить medium/low; дубли ролей и разнобой подачи из ROLES.md; спорное показать человеку |
| 10 | `cast check`, подбор голосов | предложить профили (см. «Каст») и получить согласие на пробы |
| 11 | `pron scan` → `lexicon.json` | предложить IPA для имён и терминов (status: proposed) |
| 12 | `check` | исправить всё до нуля ошибок |
| 13 | `pilot plan --sections <глава>` → `pilot run --yes` | пилот на одной главе с диалогами (можно до вычитки); `pilot/CALIBRATION.md` |
| 14 | человек слушает пилот (`review --all`) | по таблице «куда вносить поправки» правишь каст, BOOK_NOTES, паузы, словарь |
| 15 | человек вычитывает → `approve` | только по указанию |
| 16 | `freeze` → `plan` | показать план пользователю (цена уже по темпу пилота) |
| 17 | `synth --yes` | после разрешения; Batch по умолчанию (большие пакеты сами идут через Files API) |
| 18 | `batch status/collect --all` | забрать результаты |
| 19 | `qc run` → `review` | страница `qc/<релиз>/review.html`: человек слушает и жмёт принять/отклонить |
| 20 | `qc apply decisions-<релиз>.json` | применить решения со страницы; отклонённое → `synth --yes` |
| 21 | `assemble` → `qc splices --asr` | отчёт `SPLICES.md` |
| 22 | `master` | после закрытия всех подозрений |
| 23 | `publish --library <папка>` | книга в библиотеку плеера; выкладка на сервер — только с разрешения пользователя (player/README.md) |
| — | `costs` | панель затрат `costs.html`; `costs --all` — по всем проектам |

**Пилот обязателен перед первой книгой с новым кастом.** Он показывает темп каждого голоса, переигранную
подачу, неверные ударения и неудачные паузы на 5–10 минутах аудио, а не на всей книге, и уточняет цену.

**Ремарки рассказчика группой.** Если в пилоте «— сказал он» звучит оторванно, включите
`chunking.group_remarks = true`: короткие ремарки одной сцены синтезируются одним запросом и режутся по паузам.
`qc run` проверяет нарезку (и каждую часть распознаванием); при сбое — находка «нарезка группы» → `qc reject`.

## Параллельная атрибуция

Длинную книгу размечают несколько агентов одновременно. Ведущий агент:
1. пишет `BOOK_NOTES.md`, заводит главных героев (`cast add`), выполняет `attribute prepare`;
2. запускает исполнителей; каждому одна инструкция: «`attribute claim --worker <имя> --count 3`, ответь на
   выданные пакеты в `attribution/responses/<пакет>.json` по разделу „Как отвечать на пакет“, затем снова claim,
   пока пакеты не кончатся. Не запускай import, не меняй script/ и cast.json»;
3. следит за `attribute status` (free / claimed / answered / applied / error);
4. сам выполняет `attribute import` (один процесс — без гонок за файлы сценария) и отдаёт пакеты с ошибками
   обратно (`attribute unclaim <пакет>` и правка ответа);
5. проверяет `attribution/ROLES.md`: один персонаж под двумя ID, похожие EP_-роли, разнобой подачи.
   Захват старше 2 часов без ответа можно перехватить другим исполнителем.

## Как отвечать на пакет атрибуции

Пакет содержит правила, роли, заметки о книге, контекст и блоки в JSONL.
1. Прочитай весь пакет и контекст. Для каждого блока найди основание: ремарку, обращение, ответ на вопрос,
   грамматический род, кто присутствует в сцене.
2. Для каждого блока заполни `speaker_id`, `mode`, `style`, `confidence`, `evidence`. Поле `text`
   добавляй только при правке: CAPS, ё, тег или пунктуация.
3. Смешанный блок (речь и ремарка вместе) разбей через `splits`, сохранив слова и порядок.
4. Новые роли объяви в `new_roles` с описанием для подбора голоса: возраст, характер, манера.
5. style пиши редко и коротко: большинство реплик нейтральны. У рассказчика style всегда пустой.
6. Сохрани ответ как JSON в `attribution/responses/<имя>.json` и выполни `attribute import`.
   Если импорт вернул ошибки, исправь именно их и повтори.
7. Самопроверка: каждый id ровно один раз; нет `UNKNOWN`; low — только там, где действительно угадано.

## Каст

- Для каждой роли нужен профиль, у профиля — голос. Главным персонажам — свои профили. Эпизодические
  роли могут делить профиль, если не встречаются в одной сцене (`cast check` покажет конфликты).
- Студийные голоса выбирай по описаниям в GEMINI_TTS.md §4 и полу персонажа: `cast assign --profile V02 --voice Charon`.
  Для особых персонажей предложи Voice design: английский `design_prompt` из 1–2 предложений (возраст,
  тембр, фактура, манера), не больше.
- Голос утверждается только после русских проб (`cast audition --yes`, платно) и прослушивания человеком.
- Для озвучки нескольких книг одним рассказчиком перенеси профиль: `cast import --path <voice_plan.json>`.

## Произношение

- `pron scan` → `pronunciation/candidates.md`: имена, латиница, цифры, CAPS.
- Добавь записи: `pron add --form Халландрен --say "/xɐˈlandrʲɪn/" --note "ударение на ла́н"`.
  IPA для русского: `ˈ` перед ударным слогом; безударное «о/а» после твёрдых → `ɐ` (предударный) или `ə`;
  мягкость — `ʲ`; «ы» — `ɨ`; «щ» — `ɕː`; «ц» — `t͡s`; «ч» — `t͡ɕ`; безударное «е/я» после мягких → `ɪ`.
  Каждую словоформу пиши отдельно: «Халландрен», «Халландрена», «Халландрене».
- Для омонимов добавь `--context "регулярка"`.
- Предложенные записи проверяются пробой: `pron trial --text "…" --name x --yes` (платно, с разрешения).
  Затем человек слушает и даёт команду `pron accept`.
- Числа и аббревиатуры правь в самом сценарии словами (с полем `edit`), а не через словарь.

## Короткие тексты: реклама, слоганы, рилсы

```
python vox.py init projects/studio --kind clips
# пишешь projects/studio/clips/<кампания>.md по docs/SCRIPT_GUIDE.md
python vox.py --book projects/studio clips plan clips/<кампания>.md
python vox.py --book projects/studio clips render clips/<кампания>.md --yes   # после разрешения
python vox.py --book projects/studio say "Текст" --voice Kore --style "Warm." --takes 3 --yes
```
Результат: `out/<кампания>/<блок>/take-N.{wav,mp3}`, `.srt` и `index.md`. Громкость −14 LUFS для соцсетей.
Предлагай 2–3 дубля и 2 варианта подачи. Хронометраж оценивай заранее: ≈2–2,5 слова в секунду.
Точные субтитры для рилсов: `--subs asr` (нужен `qc.asr`), для готового файла — `vox.py subs файл.wav --text "…"`.

**Библиотека голосов** (`library/voices.json`, общая для всех проектов): фирменный голос компании —
`voices add --name brand --voice Kore --style "Warm, confident."`, затем в сценарии просто `voice: brand`.
Созданные голоса (voice design) регистрируются там сами; `voices list --expiring 30` покажет, чьи голоса
скоро удалит Google (срок год). `voices use --name brand --profile V05` подключает голос к касту книги.

Разовый вызов без проекта: `python tts.py "…" --voice Kore -o out/x.wav --yes`. Кэша и журнала здесь нет,
поэтому для работы используй проекты.

## Разбор проверки (QC)

- `qc/<релиз>/REPORT.md`: по каждому подозрению укажи пользователю job, время и что слушать.
- Сначала идут сигналы, которые подтвердили оба движка или аномалия Gemini плюс сигнал GigaAM, затем
  «техника», затем одиночные сигналы.
- Если подозрение — явный авторский повтор, который есть в тексте, напиши об этом. Решение `accept`
  всё равно принимает человек.
- Перегенерация: только после `qc reject` по решению человека и с разрешением на оплату.

## Что сообщать пользователю

- После каждого этапа: что сделано, цифры (блоки, роли, запросы, длительность), что требует его решения.
- Перед оплатой: план, оценка цены, объём. Спроси разрешение одним сообщением.
- Ошибки API: код, сколько запросов успело пройти, что заблокировано. Без повторов.
- Не пересказывай весь отчёт: давай ссылку на REPORT.md, SPLICES.md или REVIEW.md и 3–5 главных пунктов.

## Тесты

`python -X utf8 check.py` — компиляция и офлайн-тесты, без сети и оплат (поддельный клиент Gemini).
Запускай после любой правки кода харнесса; `check.py --install-hook` ставит проверку перед каждым коммитом,
а `.github/workflows/tests.yml` гоняет её в GitHub на Windows и Linux. Новая функция — новый тест в `tests/`.
